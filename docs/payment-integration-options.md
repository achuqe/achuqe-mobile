# „აჩუქე“-ს აპშიდა გადახდის ინტეგრაციის არჩევანი

## მიზანი

მომხმარებელი გადაიხდის თანხას „აჩუქე“-ს checkout-იდან ბანკის დაცულ გადახდის გვერდზე. პლატფორმა შეინახავს მთლიან თანხას, საკუთარ საკომისიოს და ბიზნესისთვის დასარიცხ თანხას. შეკვეთა ბიზნესის სამუშაო სივრცეში მხოლოდ **დადასტურებული გადახდის** შემდეგ უნდა გამოჩნდეს.

> ბარათის მონაცემები „აჩუქე“-ს სერვერზე არ უნდა გაიაროს და არ უნდა შეინახოს. აპლიკაცია მხოლოდ ქმნის გადახდის სესიას, მომხმარებელს გადაჰყავს ბანკის გვერდზე და საბოლოო სტატუსს ბანკის callback-ით ამოწმებს.

## შედარება

| მიდგომა | მომხმარებლის გამოცდილება | კომისიის კონტროლი | დაყენების სირთულე | შეზღუდვა |
|---|---|---:|---:|---|
| **TBC E-Commerce** | აპი ქმნის გადახდას და მომხმარებელს უსაფრთხო TBC checkout-ზე გადაჰყავს | მაღალი; თანხა პლატფორმის merchant ანგარიშზე მიიღება | საშუალო | საჭიროა TBC-ის merchant/onboarding და callback URL-ის დამტკიცება |
| **Bank of Georgia Payment Manager** | აპი ქმნის გადახდის მოთხოვნას და მომხმარებელს ბანკის გადახდის გვერდზე გადაჰყავს | მაღალი; იგივე marketplace მოდელის მხარდაჭერაა | საშუალო | საჭიროა Bank of Georgia-ს ბიზნეს-ანგარიში და merchant ჩართვა |
| **პირდაპირი გადახდა ბიზნესთან** | მომხმარებელი უკავშირდება ბიზნესს ან გადადის მის ბმულზე | დაბალი; შეკვეთიდან საკომისიოს ავტომატური ჩამოჭრა ვერ კონტროლდება | დაბალი | არ აკმაყოფილებს აპშიდა საკომისიის მოთხოვნას |

ორივე ბანკის ოფიციალური დოკუმენტაცია აღწერს redirect checkout-სა და სერვერულ callback-ს. TBC-ის API-ს გადახდის ინიციაციისთვის სჭირდება access token და API key; საბოლოო სტატუსის ცვლილებისას callback URL-ზე იგზავნება `PaymentId`, რომლის შემდეგაც merchant უნდა ამოწმებდეს რეალურ სტატუსს. [1] Bank of Georgia-ს Payment API ასევე იყენებს HTTPS/JSON, OAuth 2.0/JWT და callback შეტყობინებებს გადახდის დადასტურებისა და განახლებისთვის. [2]

## რეკომენდებული ტექნიკური წესები

გადახდის ინიციაციისას სერვერი შექმნის უნიკალურ payment ჩანაწერს `pending` სტატუსით. ბანკის callback-ის მიღებისას სერვერი **უნდა გადაამოწმოს გადახდის სტატუსი ბანკის API-ით**, მხოლოდ ამის შემდეგ მონიშნოს გადახდა `paid`, შექმნას ბიზნესის notification და გახადოს შეკვეთა დასამუშავებლად. Browser return URL გამოიყენება მხოლოდ მომხმარებლისთვის წარმატების/წარუმატებლობის ეკრანის საჩვენებლად — იგი არ არის გადახდის საბოლოო მტკიცებულება.

ამ ვერსიისთვის პლატფორმის საკომისიო განისაზღვრება შეკვეთის ჯამის **6%-ად**. `grossAmount` არის მომხმარებლის მიერ გადახდილი თანხა; `platformFee` არის `grossAmount × 6%`; `businessPayout` არის `grossAmount - platformFee` ანუ 94%. merchant ანგარიშების დამატებამდე აპი მხოლოდ ტესტურ გადახდის დადასტურებას გამოიყენებს და რეალურ ფულად ჩამოჭრას არ შეასრულებს. თანხის რეალური ჩარიცხვა ბიზნესისთვის უნდა მოხდეს მხოლოდ მას შემდეგ, რაც ბიზნესთან კონტრაქტი, settlement გრაფიკი და refund წესები ჩამოყალიბდება.

## აუცილებელი გადაწყვეტილება

პროექტის გადაწყვეტილებით checkout მხარს დაუჭერს **ორივე ბანკს** — TBC-სა და Bank of Georgia-ს. მომხმარებელი თავად აირჩევს პროვაიდერს, ხოლო შეკვეთის, საკომისიოსა და ბიზნესის დასარიცხი თანხის ლოგიკა ერთიანი დარჩება. შემდეგ ეტაპზე საჭირო იქნება თითოეული merchant ანგარიშის production API წვდომა, callback URL-ის დამტკიცება და ბიზნესთან თანხის განაწილების წესები.
